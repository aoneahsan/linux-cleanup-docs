# रिकवरी

**linux-cleanup में कोई अनडू नहीं है।** यह पेज यह समझने के बारे में है कि क्या हटा और आपके असली विकल्प क्या हैं।

:::danger पहले डिस्क पर लिखना बंद करें
अगर कुछ अपूरणीय हटा है और आप फ़ाइल-कार्विंग से वापस लाने की कोशिश करना चाहते हैं, तो **अभी फ़ाइल सिस्टम का इस्तेमाल बंद करें**। हर लिखाई अनलिंक हुए डेटा को वापस पाने की संभावना घटाती है।

यह केवल [सच में अपूरणीय श्रेणियों](#3-decide-what-is-actually-recoverable) पर लागू होता है। कैश के लिए इसे छोड़ दें — बस टूल को फिर से लाने दें।
:::

## 1. उपलब्ध रिकॉर्ड देखें {#1-inspect-the-available-record}

एक रन स्थानीय लॉग छोड़ सकता है। गाइडेड वॉकथ्रू एक JSON सत्र रिकॉर्ड भी छोड़ सकता है, अगर रिपोर्टिंग बंद न की गई हो। दोनों में से कोई पूरी फ़ाइल-दर-फ़ाइल हटाने की सूची या बैकअप नहीं है।

```bash
# सबसे हाल का सत्र लॉग
less "$(ls -t ~/.linux-cleanup/logs/cleanup-*.log | head -1)"

# सबसे नया वॉकथ्रू रिकॉर्ड, अगर हो
jq '.' "$(ls -t ~/.linux-cleanup/reports/report-*.json | head -1)"
```

बचे हुए लॉग में किसी ख़ास पथ को ढूँढने के लिए:

```bash
grep -rn 'the-filename-you-are-missing' ~/.linux-cleanup/logs/
```

कोई मिलान न मिलना यह साबित नहीं करता कि टूल ने उस फ़ाइल को छोड़ दिया। कोई सहायक हर फ़ाइल के बजाय पूरा कैश फ़ोल्डर या एक कमांड बता सकता है, और `--cleanup-logs` किसी रन का लॉग हटा सकता है। चुना गया मोड और लक्ष्य जड़ें भी जाँचें।

एक सत्र के चरणों तक सीमित करने के लिए:

```bash
jq '.steps[] | select(.status == "ran")' \
  "$(ls -t ~/.linux-cleanup/reports/report-*.json | head -1)"
```

## 2. पुष्टि करें कि बस मना तो नहीं किया गया {#2-confirm-it-was-not-simply-refused}

इनकार भी लॉग होते हैं। अगर ऐसी पंक्ति मिले, तो कुछ नहीं हटा:

```text
✗ REFUSE: protected path: /home/you/Documents/notes
```

देखें [संरक्षित पथ](./reference/protected-paths.md)।

## 3. तय करें कि असल में क्या वापस आ सकता है {#3-decide-what-is-actually-recoverable}

| क्या हटा | रिकवरी |
|---|---|
| पैकेज मैनेजर कैश | **अपने आप।** अगला इंस्टॉल उसे फिर डाउनलोड करता है |
| ब्राउज़र कैश | **अपने आप।** ब्राउज़ करते हुए फिर बनता है |
| Gradle कैश या wrapper वितरण | **अपने आप।** अगला बिल्ड फिर लाता है — पहला बिल्ड धीमा होगा |
| Cypress / Playwright बाइनरी | उस टूल का इंस्टॉल चरण फिर चलाएँ |
| `node_modules` | प्रोजेक्ट में `yarn install` या `npm install` |
| Android AVD | Android Studio में फिर बनाएँ। **प्रोफ़ाइल कॉन्फ़िग चला गया**; सिस्टम इमेज फिर डाउनलोड होती है |
| एडिटर एक्सटेंशन संस्करण | एडिटर विंडो फिर लोड करें; सच में ग़ायब हो तो फिर इंस्टॉल करें |
| apt कैश, जर्नल, snap संशोधन | अपने आप फिर बनते हैं। कुछ नहीं करना |
| **`~/Downloads` से निजी फ़ाइल** | **केवल आपके अपने बैकअप से**, या स्रोत से फिर डाउनलोड |
| **अधूरा डाउनलोड** | वापस नहीं आता। डाउनलोड फिर शुरू करें |

### आम चीज़ें फिर से बनाना {#regenerating-the-common-ones}

```bash
# प्रभावित प्रोजेक्ट में
yarn install            # या: npm install / pnpm install

# टेस्ट-रनर बाइनरी
npx cypress install
npx playwright install

# Flutter
flutter pub get
```

इनमें टूल की कोई ज़रूरत नहीं — आप बस हर टूल को वही करने दे रहे हैं जो वह खाली कैश पर करता है।

## 4. अगर सच में अपूरणीय था {#4-if-it-was-genuinely-irreplaceable}

वास्तविक रूप से, क्रम से:

1. **आपका अपना बैकअप।** Timeshift, Borg, restic, rsync स्नैपशॉट, क्लाउड सिंक — जो भी आप चलाते हों। यही अकेला भरोसेमंद जवाब है।
2. **मूल स्रोत।** डाउनलोड की गई फ़ाइल फिर डाउनलोड की जा सकती है। URL के लिए ब्राउज़र हिस्ट्री देखें।
3. **किसी सिंक सर्विस का ट्रैश।** Dropbox, Nextcloud, Google Drive जैसे हटाई गई फ़ाइलें सर्वर पर कुछ समय रखते हैं। अगर फ़ोल्डर सिंक था, तो वहाँ देखें।
4. **फ़ाइल-कार्विंग टूल** — `extundelete`, `testdisk`, `photorec`। ये अनलिंक हुए inode पर काम करते हैं और व्यस्त फ़ाइल सिस्टम पर, ख़ासकर TRIM वाले SSD पर, बहुत कम उम्मीद रखते हैं। पहले फ़ाइल सिस्टम अनमाउंट करें या live USB से काम करें, और वापस मिला डेटा कभी उसी डिवाइस पर न लिखें।

:::caution चरण 4 के बारे में अपने साथ ईमानदार रहें
माउंट किए हुए, सक्रिय रूप से इस्तेमाल हो रहे TRIM वाले SSD पर कार्विंग से आम तौर पर कुछ नहीं मिलता। यह केवल सच में ज़रूरी चीज़ के लिए आज़माने लायक है, और वह भी डिस्क पर लिखना बंद करने के बाद।
:::

## 5. इसे दोबारा होने से रोकें {#5-stop-it-happening-again}

| बदलाव | असर |
|---|---|
| हर सफ़ाई से पहले [`--scan`](./modes/scan.md) चलाएँ | नतीजा तब दिखता है जब वह अभी सिर्फ़ संभावना है |
| कीमती चीज़ें `~/Downloads` से बाहर रखें | `~/Documents` और `~/Desktop` [संरक्षित](./reference/protected-paths.md) हैं |
| वॉकथ्रू में चरण 7 छोड़ें | तब निजी फ़ाइलों के लिए एक सोचा-समझा अलग रन चाहिए |
| सीमा बढ़ाएँ: `-d 365` | केवल सच में बहुत पुरानी फ़ाइलें उम्मीदवार बनती हैं |
| भरोसेमंद मशीन पर `--all-safe` के अलावा `-y` कभी न लगाएँ | `-y` निजी डेटा नहीं छू सकता, पर फ़ैसले आपको बाद में ही दिखते हैं |
| असली बैकअप बनाएँ | यही अकेली चीज़ है जो किसी भी हटाने को वापस लाने लायक बनाती है |

## 6. अगर टूल ने वह किया जो उसे नहीं करना चाहिए था {#6-if-the-tool-did-something-it-should-not-have}

अगर किसी [संरक्षित पथ](./reference/protected-paths.md) के भीतर कुछ हटा, या एडिटर एक्सटेंशन का *मौजूदा* संस्करण हटा, या कुछ और ऐसा हुआ जो दस्तावेज़ में बताई जाँचों के उलट हो — तो वह रिपोर्ट करने लायक बग है।

```bash
linux-cleanup --debug-bundle
linux-cleanup --feedback
```

लॉग और, हो तो, वॉकथ्रू रिकॉर्ड साथ दें। देखें [बग रिपोर्ट भेजें](./guides/send-a-bug-report.md)।
