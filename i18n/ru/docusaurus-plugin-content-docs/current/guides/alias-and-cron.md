# Псевдоним оболочки и еженедельный cron

**Две вспомогательные настройки, которые делаются один раз: псевдоним оболочки `cleanup` и еженедельный автоматический запуск.** Обе отменяются соответствующим флагом удаления.

```bash
linux-cleanup --install-alias
linux-cleanup --install-cron
```

## Псевдоним оболочки {#the-shell-alias}

```bash
linux-cleanup --install-alias
```

Добавляет псевдоним `cleanup` в `~/.bash_aliases` или `~/.zshrc` — в зависимости от оболочки. После этого набор `cleanup` в любом месте запускает инструмент.

Перезапустите оболочку, иначе покажется, что псевдонима нет:

```bash
source ~/.bashrc     # или ~/.zshrc
```

Удаляется командой `linux-cleanup --uninstall-alias`.

:::note Файлы инициализации оболочки защищены на уровне удаления
`.bashrc`, `.zshrc`, `.bash_aliases` и подобные входят в [список защищённых имён файлов](../reference/protected-paths.md#protected-basenames), поэтому ни один режим очистки не может удалить такой файл — где бы он ни находился. Установщик псевдонима дописывает строку; удаление убирает только её.
:::

## Еженедельное задание cron {#the-weekly-cron-job}

```bash
linux-cleanup --install-cron
```

Планирует `--all-safe -y` **на воскресенье в 03:00** и дописывает вывод в `~/.linux-cleanup/logs/cron.log`. Нужен `crontab`.

Удаляется командой `linux-cleanup --uninstall-cron`.

### Почему здесь подходит именно `--all-safe` {#why---all-safe-is-the-right-mode-for-this}

Это единственный режим, на который действует `--yes`, и он **не может тронуть личные данные**: только интерактивные режимы в него не входят и по замыслу игнорируют `--yes`. Поэтому запуск без присмотра может очистить кэш, но никогда не удалит файл из `~/Downloads`. См. [барьер 3](../safety/guards.md#guard-3--personal-data-is-interactive-only).

[Порог простоя](../safety/guards.md#guard-2--the-staleness-gate) по-прежнему действует, так что недавно использованные файлы переживают каждый еженедельный проход.

## Своя запись в crontab {#writing-the-crontab-entry-yourself}

Для другого расписания или других флагов:

```bash
crontab -e
```

```bash
0 3 * * 0 /usr/local/bin/linux-cleanup --all-safe -y --no-report --cleanup-logs >>~/.linux-cleanup/logs/cron.log 2>&1
```

:::danger Используйте абсолютный путь
cron работает с минимальным `PATH` — обычно это только `/usr/bin:/bin`. Голое имя `linux-cleanup` не найдётся, если программа лежит в `~/.local/bin` или в каталоге менеджера версий Node, и задание будет каждую неделю молча завершаться неудачей.

Это самая частая проблема запусков по расписанию. Узнайте свой путь:

```bash
command -v linux-cleanup
```

Или явно задайте `PATH=` в начале crontab.
:::

| Флаг | Зачем в cron |
|---|---|
| `--all-safe -y` | Без присмотра, только кэш |
| `--no-report` | Не даёт копиться JSON-записям — они **никогда** не удаляются автоматически |
| `--cleanup-logs` | Удаляет журнал этого запуска в конце |
| `-d 30` | Необязательно: более агрессивное еженедельное прореживание |

Одного `--cleanup-logs` мало, чтобы каталог оставался небольшим: записи сеансов он не трогает никогда. Это делает `--no-report`.

:::caution Не добавляйте `--purge-all` в задание по расписанию
Без присмотра и без порога простоя дорогой ресурс может исчезнуть за неделю до того, как понадобится, и никто этого не заметит. Оставьте `--purge-all` для осознанных запусков под присмотром. См. [Освободить больше всего места](./reclaim-the-most-space.md).
:::

## Проверка, что задание выполнилось {#checking-that-it-ran}

```bash
tail -100 ~/.linux-cleanup/logs/cron.log
crontab -l | grep -i cleanup
```

Если в журнале `command not found`, это описанная выше проблема с `PATH`. Если журнал пуст, задание ни разу не сработало — проверьте, запущен ли демон cron (`systemctl status cron` или `crond`).

Журнал cron **никогда не ротируется**. Когда он разрастётся, ротируйте его сами:

```bash
mv ~/.linux-cleanup/logs/cron.log ~/.linux-cleanup/logs/cron.log.old
touch ~/.linux-cleanup/logs/cron.log
```

## Таймер systemd вместо cron {#a-systemd-timer-instead}

Если вы предпочитаете таймеры, ничего специфичного для инструмента здесь нет — запланируйте ту же команду. Инструмент не знает и не интересуется, какой планировщик его вызвал, а `--install-cron` — удобство, а не обязательное условие.

## Удаление обоих {#removing-both}

```bash
linux-cleanup --uninstall-alias
linux-cleanup --uninstall-cron
```

Полное удаление вместе с пакетом: [Удаление](./uninstall.md).
