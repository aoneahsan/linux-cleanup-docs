# Коды выхода

**linux-cleanup следует соглашению Unix: `0` — успех, всё остальное — проблема.** Некоторые ненулевые коды ожидаемы и намеренно не считаются сбоями.

## Коды {#codes}

| Код | Значение | Пакет сбоя |
|---|---|---|
| `0` | Чистый запуск. Каждое запрошенное действие выполнено или отклонено | Нет |
| `1` | Общий сбой — нарушен инвариант. Бывает редко | Да |
| `2` | Ошибка разбора аргументов. Печатается справка | Нет |
| `3` | Публичная запись о выпусках требует обновления | Нет |
| `127` | Команда не найдена — нет обязательной зависимости | Да |
| `130` | Прервано через `Ctrl-C` (SIGINT) | Нет |
| `137` | Убит сигналом SIGKILL — обычно OOM killer или `kill -9` | Да |
| `139` | Ошибка сегментации. В чистом bash такого быть не должно | Да |
| `143` | Завершён сигналом SIGTERM | Нет |
| любой другой ненулевой | Неожиданный внутренний сбой | Да |

Неизвестный флаг завершает работу с кодом `2` до очистки. `--dry-run` поддерживается: он проходит выбранный режим без удаления файлов. См. [Предпросмотр перед удалением](../safety/preview-first.md).

## Как решает обработчик сбоев {#how-the-crash-trap-decides}

Обработчик EXIT, добавленный в [1.3.0](../changelog.md#130--2026-05-10), проверяет в таком порядке:

1. Код выхода `0` **или** скрипт выставил внутренний признак завершения → пакета нет
2. Код выхода `130` (`Ctrl-C`) или `143` (SIGTERM) → пакета нет. Остановка пользователем — не сбой
3. Код выхода `2` (разбор аргументов) → пакета нет. Скрипт напечатал справку и остановился намеренно
4. Всё остальное → запись `crash-<timestamp>.tar.gz` в `~/.linux-cleanup/feedback/`

В пакете текущий журнал сеанса, последняя JSON-запись и краткий манифест системы. Он остаётся на вашей машине — **ничего не отправляется**. Инструмент печатает путь, чтобы вы могли просмотреть пакет и решить, отправлять ли его по почте.

См. [Отправить отчёт об ошибке](../guides/send-a-bug-report.md).

## Ветвление по коду {#branching-on-the-code}

```bash
if linux-cleanup --scan; then
  echo "сканирование прошло"
else
  case $? in
    2)   echo "неверный флаг" ;;
    127) echo "нет зависимости — запустите --self-test" ;;
    130) echo "прервано пользователем" ;;
    *)   echo "неожиданный сбой — смотрите ~/.linux-cleanup/feedback/" ;;
  esac
fi
```

## В cron {#in-cron}

```bash
linux-cleanup --all-safe -y --no-report --cleanup-logs >>~/.linux-cleanup/logs/cron.log 2>&1 || \
  echo "linux-cleanup exited $?" | mail -s "cleanup failed on $(hostname)" you@example.com
```

Код `127` в задании cron почти всегда означает, что crontab использует имя команды без пути, а минимальный `PATH` cron её не нашёл. Укажите абсолютный путь — см. [Устранение неполадок](../troubleshooting.md#cron-entry-runs-but-does-nothing).

## Разбор неожиданного кода по пакету сбоя {#diagnosing-an-unexpected-code-from-a-crash-bundle}

Код выхода записан в манифесте пакета. Самые частые:

| Код | Обычная причина |
|---|---|
| `137` | OOM killer (нехватка памяти). Обычно `find` по огромному дереву |
| `141` | SIGPIPE — канал закрылся раньше времени, часто при выходе `tee` или пейджера |
| `139` | Ошибка сегментации — здесь её быть не должно никогда; сообщите о ней |
| `127` | Нет зависимости. Запустите `--self-test`, чтобы узнать, какой |
