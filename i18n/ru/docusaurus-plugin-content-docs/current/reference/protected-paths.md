# Защищённые пути

**Это пути, которые linux-cleanup отказывается удалять.** Отказ безусловный — его не отменяет ни один флаг, даже `--purge-all`.

Перед проверкой каждый кандидат разрешается через `realpath`, поэтому символическая ссылка внутрь защищённого каталога отклоняется по разрешённому пути, а не по самой ссылке.

:::tip Проверяйте на своей установке, а не верьте этой странице на слово
Списки меняются от версии к версии, а в пересказах об этом инструменте ходят каталоги, которые на самом деле **не** защищены.

```bash
linux-cleanup --list-targets   # списки так, как их видит ваша сборка
linux-cleanup --self-test      # проверяет, что защита срабатывает на известных путях
```
:::

## Три отдельных списка {#three-separate-lists}

Защита собрана из трёх списков с разными правилами совпадения. Разница важна — именно она позволяет чистить `~/.npm/_cacache`, оставляя сам `~/.npm` нетронутым.

| Список | Совпадает с | Назначение |
|---|---|---|
| Защищённые пути | Путь **и всё, что под ним** | Личные данные, учётные данные, настройки |
| Точные защищённые | **Только этот путь целиком** | Корни установки менеджеров пакетов |
| Защищённые имена | **Любой файл с таким именем, где угодно** | Файлы инициализации и истории оболочки |

## Системные корни {#system-roots}

Отклоняются как сам путь или как любой вложенный элемент, если не указано иное.

| Путь | Вложенное тоже отклоняется |
|---|---|
| `/` | — (сам корень) |
| `/home` | Нет — только сам путь |
| `/root` | Нет — только сам путь |
| `/etc` | **Да** |
| `/boot` | **Да** |
| `/usr` | **Да** |
| `/var` | Нет — только сам путь |
| `/lib` | Нет — только сам путь |
| `/sbin` | Нет — только сам путь |
| `/bin` | Нет — только сам путь |
| `$HOME` | Нет — только сам корень домашнего каталога, чтобы голый `$HOME` нельзя было стереть |

:::note `/proc` и `/sys` в этом списке нет
Ни одна цель очистки к ним не приближается, но в списке разрешённых путей они явно не названы. Некоторые описания инструмента утверждают обратное. Это не так.
:::

## Личные каталоги {#personal-directories}

Отклоняются вместе со всем содержимым.

| Путь | Что хранит |
|---|---|
| `~/Documents` | Документы |
| `~/Pictures` | Изображения |
| `~/Music` | Аудио |
| `~/Videos` | Видео |
| `~/Desktop` | Содержимое рабочего стола |
| `~/Public` | Общие файлы |
| `~/Templates` | Шаблоны документов |

:::caution `~/Downloads` намеренно НЕ защищён
Иначе нельзя — очистка крупных давно не используемых файлов там и есть функция ([Давно не используемые личные файлы](../modes/personal-stale-files.md)). Его защищает [барьер 3](../safety/guards.md#guard-3--personal-data-is-interactive-only): только интерактивно, подтверждение по каждому файлу, `--yes` игнорируется.

Если в `~/Downloads` лежит что-то незаменимое, перенесите это в защищённый каталог. Это надёжное решение.
:::

## Учётные данные, настройки и состояние агентов {#credentials-configuration-and-agent-state}

| Путь | Что хранит |
|---|---|
| `~/.ssh` | Ключи SSH и известные хосты |
| `~/.gnupg` | Связка ключей GPG |
| `~/.config` | Настройки приложений (очень широко) |
| `~/.gnome` | Настройки GNOME |
| `~/.mozilla` | Профили Firefox |
| `~/.thunderbird` | Профили Thunderbird |
| `~/.claude` | Состояние Claude Code |
| `~/.local/share/claude` | Данные Claude Code |

:::danger Два пути, которые часто называют защищёнными, НЕ защищены
**`~/.password-store`** (pass) и **`~/.aws`** (учётные данные AWS) в защищённом списке исходников **отсутствуют**. Некоторые статьи об инструменте утверждают обратное.

На практике ни одна цель очистки на них не указывает, так что при обычной работе они в безопасности — но не рассчитывайте, что их защитит список разрешённых путей. Если нужна такая гарантия, сначала проверьте `--list-targets` на своей установке.
:::

Защита `~/.mozilla` не мешает очистке кэша Firefox: кэш лежит в `~/.cache/mozilla`, это другое дерево.

## Защищённые пути с точным совпадением {#exact-match-protected-paths}

Совпадение **точное** — вложенное по-прежнему можно чистить. Так сохраняются глобально установленные пакеты, а восстанавливаемый кэш внутри каждого корня установки всё равно можно проредить.

| Экосистема | Пути |
|---|---|
| pnpm | `~/.local/share/pnpm` и его `global`, `bin`, `nodejs` |
| npm | `~/.npm`, `~/.npm-global`, `~/.npm-global/lib`, `~/.npm-global/lib/node_modules` |
| yarn | `~/.yarn`, `~/.config/yarn/global` |
| bun | `~/.bun`, `~/.bun/install`, `~/.bun/install/global` и его `node_modules`, `~/.bun/bin` |
| deno | `~/.deno`, `~/.deno/bin` |
| Менеджеры версий Node | `~/.volta`, `~/.volta/bin`, `~/.nvm`, `~/.nvm/versions`, `~/.fnm` |
| Rust | `~/.cargo`, `~/.cargo/bin`, `~/.rustup` |
| Go | `~/go`, `~/go/bin` |

Этот список появился из-за реального дефекта: до [1.1.0](../changelog.md#110--2026-05-10) очистка pnpm была нацелена на `~/.local/share/pnpm` — корень установки — и удаляла глобальные пакеты вместе с самим бинарным файлом `pnpm`. Исправление сузило цель до `~/.local/share/pnpm/store` и добавило этот список, чтобы ошибка не повторилась.

[`--all-safe`](../modes/all-safe.md) вдобавок при запуске проверяет, что ни один из них не попал в его список целей, и прерывается с сообщением `BUG:`, если попал.

## Защищённые имена файлов {#protected-basenames}

Отклоняются **по имени файла, в любом месте**, независимо от ведущего к ним пути:

`.bashrc` · `.bash_profile` · `.bash_login` · `.profile` · `.bash_logout` · `.zshrc` · `.zshenv` ·
`.zprofile` · `.zlogin` · `.zlogout` · `.bash_aliases` · `.bash_history` · `.zsh_history` · `.inputrc` ·
`.dircolors` · `.config` · `.local`

Это последний рубеж. Он нужен, чтобы будущая ошибка, которая каким-то образом добавит файл инициализации оболочки в список целей, всё равно не смогла его удалить.

## Как выглядит отказ {#what-a-refusal-looks-like}

```text
✗ REFUSE: protected path: /home/you/Documents/notes
✗ REFUSE: unsafe path: '/home/you'
✗ REFUSE: shell-init / history file: /home/you/.bashrc
```

Отказ — правильное поведение, а не ошибка, которую нужно обходить. Если кэш, который вы хотите очистить, отклоняется, причина почти всегда в символической ссылке, ведущей в защищённое место, — исправьте ссылку, а не инструмент. См. [Устранение неполадок](../troubleshooting.md#refuse-protected-path).
