# Схема отчёта

**Пошаговый сценарий пишет JSON-запись с `"schema_version": 1`**, если не заданы `--no-report` или `--dry-run`. Отдельный `--scan` этот отчёт не пишет. Для машиночитаемого сканирования используйте `--scan --json-events`; у этого потока другая структура.

:::warning Старая документация описывает другую структуру
Некоторые материалы — включая справочную страницу в репозитории исходников — описывают форму вокруг `schema` (строка вроде `linux-cleanup/report/v1`) с объектами `tool`, `session` и `categories`.

**Инструмент такого не выдаёт.** Парсер, написанный под эту форму, упадёт на любом настоящем файле. Ниже — то, что на самом деле пишет `modules/walkthrough.sh`. Проверьте на своей машине:

```bash
jq 'keys' "$(ls -t ~/.linux-cleanup/reports/report-*.json | head -1)"
```
:::

## Верхний уровень {#top-level}

```json
{
  "schema_version": 1,
  "credits": { },
  "meta":    { },
  "disk":    { "before": {}, "after": {} },
  "memory":  { "before": {}, "after": {} },
  "steps":   [ ],
  "totals":  { }
}
```

| Ключ | Тип | Содержит |
|---|---|---|
| `schema_version` | число | Сейчас `1`. Отклоняйте всё, что не узнаёте |
| `credits` | объект | Сведения об инструменте, лицензия и автор |
| `meta` | объект | Контекст сеанса — когда, где, как и с какими настройками |
| `disk` | объект | Занятость файловой системы до и после |
| `memory` | объект | Использование памяти до и после |
| `steps` | массив | По элементу на каждый выполнявшийся шаг |
| `totals` | объект | Итоги сеанса |

## `credits` {#credits}

```json
{
  "tool": "linux-cleanup",
  "tool_version": "2.1.1",
  "tool_homepage": "https://linux-cleanup.aoneahsan.com",
  "tool_license": "MIT",
  "author": {
    "name": "Ahsan Mahmood",
    "email": "aoneahsan@gmail.com",
    "website": "https://aoneahsan.com",
    "linkedin": "https://linkedin.com/in/aoneahsan"
  }
}
```

Это нужно, чтобы запись сама указывала своё происхождение, куда бы она ни попала. Ничего здесь не описывает вашу машину.

## `meta` {#meta}

| Ключ | Тип | Содержит |
|---|---|---|
| `tool` | строка | Всегда `linux-cleanup` |
| `tool_version` | строка | Версия, записавшая отчёт. Логику потребителя стройте на ней |
| `started_at` | строка | Отметка времени начала сеанса |
| `finished_at` | строка | Отметка времени конца сеанса |
| `duration_seconds` | число | Фактическая длительность |
| `host` | строка | Вывод `hostname` |
| `user` | строка | `$USER` |
| `mode` | строка | Запущенный режим — `walkthrough`, `scan`, `allsafe`, `system` и т. д. |
| `stale_days` | число | Действующий порог `--days` |
| `log_file` | строка | Абсолютный путь к журналу этого сеанса |
| `launcher` | строка | Как был вызван — `bash` при прямом запуске |
| `via_npx` | число | `1` при запуске через npm, иначе `0` |

`stale_days` стоит сохранять: это разница между запуском с порогом 100 дней и запуском с `-d 30`, и она объясняет, почему два сеанса на одной машине освободили разный объём.

## `disk` и `memory` {#disk-and-memory}

Оба содержат снимки `before` и `after`, снятые в начале и в конце сеанса.

`disk` содержит поля файловой системы из `df` — файловая система, размер, занято, доступно и процент использования. `memory` — аналогичные данные из отчёта системы о памяти.

:::note `after` минус `before` — не только ваша очистка
Это замеры всей машины. Сборка, обновление пакетов или открытый браузер во время сеанса тоже их сдвигают, поэтому освобождённый объём может оказаться меньше суммы шагов — или отрицательным. См. [Устранение неполадок](../troubleshooting.md#disk-usage-grew-during-the-session).
:::

## `steps` {#steps}

Массив, по элементу на каждый выполнявшийся шаг, по порядку:

```json
{ "n": 1, "title": "Package-manager caches", "status": "ran", "freed_bytes": 13315108864 }
```

| Ключ | Тип | Содержит |
|---|---|---|
| `n` | число | Номер шага, начиная с 1 |
| `title` | строка | Понятное название шага |
| `status` | строка | `ran`, `skipped`, `skipped (quit)` или `skipped (jq missing)` |
| `freed_bytes` | число | Сколько байт освободил шаг. `0`, если пропущен |

`skipped (quit)` отмечает шаги после нажатия `q` — так видно, где была намеренная остановка, а где вы отказались от отдельного шага.

## `totals` {#totals}

| Ключ | Тип | Содержит |
|---|---|---|
| `total_reclaimed_bytes` | число | Сумма по шагам |
| `total_reclaimed_human` | строка | То же в удобном виде |
| `steps_run` | число | Шаги со статусом `ran` |
| `steps_skipped` | число | Шаги со статусом `skipped` |

## Разбор {#parsing}

```bash
LATEST="$(ls -t ~/.linux-cleanup/reports/report-*.json | head -1)"

jq '.totals.total_reclaimed_human' "$LATEST"
jq '.meta | {mode, stale_days, duration_seconds}' "$LATEST"
jq '.steps[] | select(.status == "ran") | "\(.title): \(.freed_bytes)"' "$LATEST"

# Сколько освобождено за все записанные сеансы
jq -s 'map(.totals.total_reclaimed_bytes) | add' ~/.linux-cleanup/reports/report-*.json
```

## Проверка {#validating}

Файл JSON Schema с инструментом не поставляется. Проверка структуры:

```bash
jq -e 'has("schema_version") and .schema_version == 1
       and has("meta") and has("steps") and has("totals")' \
  ~/.linux-cleanup/reports/report-*.json
```

Печатает `true` для каждого корректного файла.

## Советы по совместимости {#compatibility-guidance}

Когда пишете потребителя:

- **Ветвитесь по `schema_version`.** Незнакомое значение считайте неразбираемым, а не угадывайте
- **Считайте незнакомые ключи дополнениями.** Поля уже добавлялись в рамках версии 1 и могут добавляться снова
- **Используйте `meta.tool_version`** для поведения, которое меняется от выпуска к выпуску
- **Не рассчитывайте, что каждый режим заполняет каждый раздел.** Режимы только для чтения дают меньше шагов
- **Будьте готовы к отрицательному `total_reclaimed_bytes`.** Это разница `df`, а не сумма удалённого
