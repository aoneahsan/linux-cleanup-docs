# Восстановление

**В linux-cleanup нет отмены.** Эта страница о том, как понять, что было удалено, и какие у вас реальные варианты.

:::danger Сначала прекратите запись на диск
Если удалено что-то незаменимое и вы собираетесь пробовать восстановление методом извлечения файлов (file carving), **прекратите пользоваться файловой системой прямо сейчас**. Каждая запись снижает шанс вернуть отвязанные данные.

Это относится только к [действительно незаменимым категориям](#3-decide-what-is-actually-recoverable). Для кэша это не нужно — просто дайте программе скачать его заново.
:::

## 1. Изучите доступную запись {#1-inspect-the-available-record}

Запуск может оставить локальный журнал. Пошаговый сценарий может также оставить JSON-запись сеанса, если отчёты не отключены. Ни то ни другое не полный перечень удалённых файлов и не резервная копия.

```bash
# Самый свежий журнал сеанса
less "$(ls -t ~/.linux-cleanup/logs/cleanup-*.log | head -1)"

# Последняя запись пошагового сценария, если она есть
jq '.' "$(ls -t ~/.linux-cleanup/reports/report-*.json | head -1)"
```

Чтобы найти конкретный путь в сохранённых журналах:

```bash
grep -rn 'the-filename-you-are-missing' ~/.linux-cleanup/logs/
```

Отсутствие совпадения не доказывает, что инструмент не тронул этот файл. Вспомогательная программа может записать весь каталог кэша или команду, а не каждый файл, а `--cleanup-logs` может удалить журнал запуска. Проверьте также выбранный режим и целевые корни.

Чтобы ограничиться шагами одного сеанса:

```bash
jq '.steps[] | select(.status == "ran")' \
  "$(ls -t ~/.linux-cleanup/reports/report-*.json | head -1)"
```

## 2. Убедитесь, что это был не просто отказ {#2-confirm-it-was-not-simply-refused}

Отказы тоже пишутся в журнал. Если вы нашли строку вроде этой, ничего не удалено:

```text
✗ REFUSE: protected path: /home/you/Documents/notes
```

См. [Защищённые пути](./reference/protected-paths.md).

## 3. Определите, что действительно можно вернуть {#3-decide-what-is-actually-recoverable}

| Что удалено | Восстановление |
|---|---|
| Кэш менеджера пакетов | **Автоматически.** Следующая установка скачает его заново |
| Кэш браузера | **Автоматически.** Соберётся заново, пока вы работаете |
| Кэш Gradle или дистрибутив wrapper | **Автоматически.** Следующая сборка скачает их снова — первая сборка будет медленной |
| Бинарные файлы Cypress / Playwright | Повторите шаг установки этого инструмента |
| `node_modules` | `yarn install` или `npm install` в проекте |
| Android AVD | Создайте заново в Android Studio. **Конфигурация профиля утеряна**; образ системы скачается снова |
| Версия расширения редактора | Перезагрузите окно редактора; переустановите, если оно действительно пропало |
| Кэш apt, системный журнал, ревизии snap | Восстанавливаются сами. Ничего делать не нужно |
| **Личный файл из `~/Downloads`** | **Только из вашей резервной копии** или повторной загрузкой из источника |
| **Недокачанная загрузка** | Не восстанавливается. Начните загрузку заново |

### Как восстановить самое частое {#regenerating-the-common-ones}

```bash
# В затронутом проекте
yarn install            # или: npm install / pnpm install

# Бинарные файлы средств запуска тестов
npx cypress install
npx playwright install

# Flutter
flutter pub get
```

Ничему из этого linux-cleanup не нужен — вы просто даёте каждой программе сделать то, что она делает с пустым кэшем.

## 4. Если это было действительно незаменимо {#4-if-it-was-genuinely-irreplaceable}

Реалистично, по порядку:

1. **Ваша резервная копия.** Timeshift, Borg, restic, снимок rsync, облачная синхронизация — что бы вы ни использовали. Это единственный надёжный ответ.
2. **Исходный источник.** Скачанный файл можно скачать снова. Найдите URL в истории браузера.
3. **Корзина сервиса синхронизации.** Dropbox, Nextcloud, Google Drive и подобные некоторое время хранят удалённые файлы на сервере. Если каталог синхронизировался, ищите там.
4. **Инструменты извлечения файлов** — `extundelete`, `testdisk`, `photorec`. Они работают с отвязанными inode и мало что находят на активно используемой файловой системе, особенно на SSD с включённым TRIM. Сначала отмонтируйте файловую систему или работайте с live-USB и никогда не записывайте восстановленные данные на то же устройство.

:::caution Будьте честны с собой насчёт шага 4
На смонтированном, активно используемом SSD с TRIM извлечение обычно ничего не возвращает. Пробовать стоит только ради чего-то действительно важного и только после того, как вы прекратили запись на диск.
:::

## 5. Не допустите повторения {#5-stop-it-happening-again}

| Изменение | Результат |
|---|---|
| Запускайте [`--scan`](./modes/scan.md) перед каждой очисткой | Вы видите результат, пока он ещё гипотетический |
| Уберите ценное из `~/Downloads` | `~/Documents` и `~/Desktop` [защищены](./reference/protected-paths.md) |
| Пропускайте шаг 7 в пошаговом сценарии | Тогда для личных файлов понадобится отдельный осознанный запуск |
| Поднимите порог: `-d 365` | Кандидатами станут только действительно старые файлы |
| Не используйте `-y` вне `--all-safe` на доверенной машине | `-y` не трогает личные данные, но решения вы видите только потом |
| Настройте настоящее резервное копирование | Только оно делает любое удаление обратимым |

## 6. Если инструмент сделал то, чего не должен был {#6-if-the-tool-did-something-it-should-not-have}

Если удаление произошло внутри [защищённого пути](./reference/protected-paths.md), была удалена *текущая* версия расширения редактора или что-то ещё противоречит описанным защитам — это ошибка, о которой стоит сообщить.

```bash
linux-cleanup --debug-bundle
linux-cleanup --feedback
```

Приложите журнал и, если есть, запись пошагового сценария. См. [Отправить отчёт об ошибке](./guides/send-a-bug-report.md).
