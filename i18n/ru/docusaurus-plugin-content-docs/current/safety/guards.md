# Защиты

**Перед любым удалением linux-cleanup применяет до четырёх независимых барьеров. Путь должен пройти каждый, который к нему относится.** На этой странице объясняется, что представляет собой каждый барьер, зачем он нужен и чего он не охватывает.

Эти защиты и есть вся модель безопасности. За ними нет ни резервной копии, ни [отмены](./irreversibility.md).

## Барьер 1 — список разрешённых путей {#guard-1--the-path-allowlist}

Включён всегда. Его нельзя отключить, и никакой флаг его не обходит.

Перед любым удалением цель разрешается через `realpath` и отклоняется, если попадает на защищённый путь или внутрь него. Поскольку разрешение идёт первым, символическая ссылка не может протащить путь: если `~/.cache/yarn` — ссылка внутрь `~/Documents`, разрешённый путь окажется в `~/Documents`, барьер сработает и удаление будет отклонено.

За этим стоят три отдельных списка:

| Список | Способ совпадения | Назначение |
|---|---|---|
| Системные корни и личные каталоги | Путь или любой вложенный путь | `/etc`, `~/Documents`, `~/.ssh`, `~/.config`, … |
| Корни установки менеджеров пакетов | **Только точный путь** | `~/.local/share/pnpm`, `~/.npm`, `~/.cargo`, … |
| Файлы инициализации и истории оболочки | **Имя файла, в любом месте** | `.bashrc`, `.zshrc`, `.bash_history`, … |

Когда барьер срабатывает, в stderr появляется отказ:

```text
✗ REFUSE: protected path: /home/you/Documents/notes
```

Список точных совпадений заслуживает пояснения. `~/.npm` защищён *точно*, и именно поэтому можно очищать вложенный `~/.npm/_cacache`. Так задумано: корень установки сохраняется, а кэш внутри него, который можно создать заново, очищать разрешено. Полные списки — в разделе [Защищённые пути](../reference/protected-paths.md).

:::note Чего этот барьер не делает
Он защищает *расположения*, а не *ценность*. Незаменимое видео на 40 GB в `~/Downloads` списком разрешённых путей не защищено — `~/Downloads` не защищённый путь. Его защищает [барьер 3](#guard-3--personal-data-is-interactive-only).
:::

Режимы очистки выбирают именованные целевые пути, после чего проверка защищённых путей отклоняет опасные места назначения. Путь вне защищённого списка не становится автоматически безопасным для удаления: изучите цели каждого режима и его пробный запуск.

## Барьер 2 — порог простоя {#guard-2--the-staleness-gate}

По умолчанию: 100 дней. Появился в [1.2.0](../changelog.md#120--2026-05-10), расширен в [1.2.1](../changelog.md#121--2026-05-10).

С 1.2.0 стратегия по умолчанию — **прореживать, а не стирать**. Внутри целевого каталога файл удаляется, только если **и** его `atime`, **и** его `mtime` старше `--days`. Оставшиеся пустые каталоги убираются; сама оболочка каталога остаётся, чтобы инструмент-владелец по-прежнему находил свою структуру.

Требование обеих меток времени важно. Один `mtime` удалил бы файл, скачанный год назад и прочитанный вчера; один `atime` ненадёжен на файловых системах, смонтированных с `noatime` или `relatime`. Требовать обе — осторожный подход.

Для того, что является *инструментом*, а не кэшем, — Android AVD, версии расширений редакторов, пользовательские данные flatpak — в 1.2.1 добавлено второе условие. Такой ресурс удаляется, только если **от него не зависит ни одна активная программа И он простаивает дольше порога**. Каждый ресурс оценивается как неделимое целое, поэтому частичное прореживание не оставит наполовину удалённый профиль эмулятора.

```bash
linux-cleanup --all-safe -y -d 30    # агрессивнее: порог 30 дней
linux-cleanup --all-safe -y          # по умолчанию: 100 дней
linux-cleanup --all-safe --purge-all # барьер ВЫКЛЮЧЕН — полная очистка, поведение до 1.2.0
```

:::danger `--purge-all` полностью отключает этот барьер
С `--purge-all` каждый целевой кэш стирается целиком независимо от возраста. Именно это поведение и привело к появлению барьера: оно удаляет дистрибутивы Gradle wrapper, браузеры Playwright для старых веток выпусков и архивы yarn с зафиксированными зависимостями — каждое из этого дорого скачивать заново.

Это законный выбор перед переустановкой системы. Для повседневного использования это плохое значение по умолчанию.
:::

Баннер перед запуском сообщает, какая стратегия действует, так что неясности в том, что сейчас произойдёт, не бывает.

## Барьер 3 — личные данные только интерактивно {#guard-3--personal-data-is-interactive-only}

Режимы, которые могут затронуть личные файлы, интерактивны по правилу:

- [`--stale`](../modes/personal-stale-files.md) — крупные давно не используемые файлы в `~/Downloads` и настроенных незащищённых корнях
- [`--partials`](../modes/partial-downloads.md) — брошенные недокачанные загрузки
- [`--node-modules`](../modes/node-modules-finder.md) — каталоги зависимостей заброшенных проектов

**`--yes` к этим режимам не применяется и никогда не будет.** `--yes` автоматически подтверждает только кэш, который можно создать заново. Инструмент печатает список кандидатов, ждёт подтверждения по каждому пункту и ничего не удаляет, пока вы не ответите.

Причина в том, что у личных файлов нет признака, который могла бы прочитать программа. Ничто на диске не отличает установщик, который вы больше никогда не откроете, от единственной копии документа, который просто ещё не понадобился. Знаете только вы, поэтому инструмент отказывается угадывать.

## Барьер 4 — ограничение sudo {#guard-4--sudo-confinement}

[`--system`](../modes/system-cleanup.md) — единственный режим, вызывающий `sudo`, и только для фиксированного перечня операций: каждая — отдельный проверяемый вызов, и о каждой спрашивают отдельно.

| Операция | Ответ по умолчанию |
|---|---|
| `apt autoremove --purge -y` + `apt clean` | Да |
| `journalctl --vacuum-size=100M` | Да |
| Удаление отключённых ревизий snap | Да |
| Список установленных ядер — **ничего не удаляется** | — |
| Удаление файлов в `/tmp` с `atime` старше 7 дней | Да |
| `sync` + `sysctl vm.drop_caches=3` | **Нет** |

Скрипт не правит `/etc/sudoers`, а `--system` спрашивает о каждой операции. Если `sudo` недоступен, режим прерывается, а не продолжает работу в урезанном виде.

Два значения здесь **жёстко заданы и не зависят от `--days`**: цель очистки журнала (100 MB) и порог возраста для `/tmp` (7 дней).

## Чего не охватывает ни один барьер {#what-no-guard-covers}

Ясно назвать пробелы полезнее, чем успокаивать.

| Пробел | Что это значит |
|---|---|
| **Нет отмены** | Ничто здесь не делает удаление обратимым. См. [Удаление безвозвратно](./irreversibility.md). |
| **`~/Downloads` не защищён** | До него добирается интерактивный режим личных файлов — читайте кандидатов. `~/Desktop` защищён. |
| **`--purge-all` снимает барьер 2** | Барьеры 1, 3 и 4 действуют; порог простоя — нет. |
| **Запуск от root расширяет возможный ущерб** | Инструмент рассчитан на обычного пользователя. `--system` сам обрабатывает законные потребности в sudo. |
| **Защиты охраняют пути, а не содержимое** | Защищённый каталог в безопасности, где бы он ни был; ценный файл вне его — нет. |
| **`/proc` и `/sys` нет в защищённом списке** | На них ничто не нацелено, но список их и не называет. |

## Проверьте защиты сами {#verifying-the-guards-yourself}

```bash
npx linux-cleanup --self-test      # проверяет, что барьеры срабатывают на известных путях
npx linux-cleanup --list-targets   # печатает списки целей и защищённых путей
```

`--self-test` — честная проверка. Он проверяет, что `/`, `$HOME`, `~/Documents`, `~/.ssh` и `/etc` защищены, а `~/.cache/yarn` нет, и завершается с ненулевым кодом, если хоть одна проверка не прошла. Документация может отстать; проверка работает на том коде, который у вас действительно есть.
