FAQ

Symptom-specific problems belong in Troubleshooting; design rationale is in Safety guards.

Will it delete my code?​

Your source files, no. ~/Documents and the other personal directories are protected outright, and no cleanup target points at a project's source.

The closest it comes is finding stale node_modules directories inside your project roots. Those are interactive-only with per-project confirmation, and yarn install rebuilds them.

One caveat worth knowing: if you edited a file inside node_modules directly, rather than through a patch tool, that edit exists nowhere else.

Does it phone home?​

The CLI checks a public release record over HTTPS at start when online. It sends no scan results, cleanup paths or crash bundle. Offline, the check fails open and the run continues.

Verify it yourself on a clone:

grep -rE 'curl|wget|http://|https://' cleanup.sh lib/ modules/ bin/

The release check lives in modules/update_check.sh; inspect that file too. Installing or accepting an update uses npm or GitHub. The feedback helper opens a draft that you choose whether to send.

Why is there no undo?​

An undo log would be write amplification on the disk you are trying to free — keeping 20 GB in order to reclaim 20 GB accomplishes nothing. It would also create false confidence, and be partial at best.

The safety model is prevention instead: an allowlist, a staleness gate, and interactive confirmation. Full reasoning: Deletion is permanent.

Is there a --dry-run?​

Yes. --scan reads only; --dry-run walks the selected cleanup without deleting files or changing settings. A dry run still keeps a local log and writes no JSON session report. See Preview before deleting.

What is the safest way to try it?​

linux-cleanup --self-test      # verifies the guards actually fire
linux-cleanup --scan           # read-only; shows what would be reclaimed
linux-cleanup --list-targets   # every path it can touch
linux-cleanup --all-safe --dry-run  # preview a cache cleanup

After those three you have seen the safety model work without losing a byte. Then run linux-cleanup and answer n to anything that surprises you.

Will it speed up my computer?​

A little, sometimes, and it is worth being honest about how little:

  • VS Code launches faster with a dozen extension directories rather than fifty
  • A cold cache is marginally faster to skim than a bloated one
  • Browser cold-starts are unaffected — caches are key-value, lookups are O(1)
  • The page-cache drop frees RAM, not disk, and the kernel refills it immediately

The real benefit is that "disk full" stops blocking your work — not a benchmark number.

What if I press Ctrl-C mid-cleanup?​

The current removal finishes — usually well under a second — then the script exits with code 130. The log keeps everything up to that point. The crash trap deliberately ignores 130, so no crash bundle is written.

Can I run it as root?​

You can, but you should not. It is designed to run as a normal user, and running as root only widens the blast radius if a bug ever slipped past the guards. --system handles the legitimate sudo needs internally, one audited command at a time.

Does it work on my distro?​

Cache cleanup inside $HOME works on every Linux distribution.

--system is Debian and Ubuntu only — it calls apt and dpkg with no distro detection. On Fedora, Arch or openSUSE its package steps fail while the journal, /tmp and page-cache steps still work. See Distro support.

What about WSL?​

The CLI runs on the Linux side. Review any symlink from your Linux home into /mnt/c/ before cleanup. The allowlist resolves symlinks, but a Windows Documents path is not automatically covered by a Linux home-path rule.

Why bash rather than Python, Go or Rust?​

Bash is already on every system this targets. A compiled binary would mean shipping something users cannot easily audit; a Python or Node implementation would add a runtime dependency to a tool whose entire job is removing things from your disk.

The script is a few thousand lines of commented bash that a senior engineer can read in an afternoon. For a tool that runs rm -rf with sudo available, auditability is worth more than ergonomics.

How often should I run it?​

ModeCadence
--scanMonthly, as a baseline
--all-safe -yWeekly — automate it
--systemQuarterly, manually
--node-modulesYearly, once side projects pile up
--editor-extWhen the editor feels slow — also covered by --all-safe
--staleQuarterly, deliberately
--doctorWhen command not found appears
--globalsBefore reinstalling Node or migrating machines

What is --purge-all for?​

It disables the staleness gate, wiping caches in full rather than pruning idle files. That includes Gradle wrapper distributions, Playwright browsers and Cypress binaries you might still want.

It is the right choice before reimaging a machine and a poor default otherwise. Never combine it with a cron job.

Which version should I install?​

Check the npm package for the current published version and run linux-cleanup --version to identify your installed copy. See the changelog before upgrading.

How do I request a feature or report a bug?​

linux-cleanup --debug-bundle
linux-cleanup --feedback

Then open a GitHub issue or email aoneahsan@gmail.com. Pull requests are welcome under MIT; description-only feature requests are equally welcome. See Send a bug report.

What will it never do?​

  • Delete anything on the protected-path list
  • Touch personal data without per-file confirmation
  • Upload scan results, cleanup paths or crash bundles automatically
  • Install a service, daemon or background agent
  • Modify or remove an existing line in your shell configuration
  • Recover anything it deleted
