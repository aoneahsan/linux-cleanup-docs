What it deletes

linux-cleanup removes regenerable data: files a tool will rebuild or re-download the next time it needs them. This page is the complete inventory, grouped by how expensive each category is to get back.

Every deletion on this page is permanent. "Regenerable" means a program can recreate it, not that linux-cleanup can.

Get this list from your own machine

The authoritative list for your system, with real paths and real sizes, comes from the tool itself:

npx linux-cleanup --list-targets   # every path it can touch
npx linux-cleanup --scan           # those paths, with current sizes, deleting nothing

How to read the cost column​

Regeneration costMeaning
FreeRebuilt automatically, in seconds, without you noticing
CheapRe-downloaded on next use; costs bandwidth and a short wait
ExpensiveLarge re-download or long rebuild — minutes to hours
ManualNothing regenerates it. Gone means gone

Package-manager caches​

Downloaded archives kept so a reinstall skips the network. Deleting them slows the next install and nothing else.

TargetPathTypical sizeCost
Yarn v1~/.cache/yarn2–20 GBCheap
Yarn Berry~/.yarn/berry/cache1–8 GBCheap
npm~/.npm/_cacache1–10 GBCheap
npx~/.npm/_npx100 MB–2 GBCheap
pnpm store~/.local/share/pnpm/store2–15 GBCheap
pip~/.cache/pip200 MB–3 GBCheap
Composer~/.composer/cache100 MB–2 GBCheap
bun~/.bun/install/cache100 MB–2 GBCheap
deno~/.cache/deno100 MB–2 GBCheap
The install directories are protected, only the caches are cleaned

~/.local/share/pnpm (which holds your globally installed packages and the pnpm binary itself), ~/.npm, ~/.yarn, ~/.bun/install/global and ~/.deno/bin are on the exact-match protected list. Only the regenerable store or cache inside them is targeted.

This distinction was a real bug: before 1.1.0 the pnpm cleanup targeted ~/.local/share/pnpm and wiped globally installed packages. See the changelog.

Browser and application caches​

Chrome / Chromium / Brave / Edge / Vivaldiprofile Cache/ dirs500 MB–8 GBFree

Gradle build cache~/.gradle/caches3–10 GBCheap
Gradle wrapper distributions~/.gradle/wrapper/dists200 MB–3 GBExpensive
Cypress binaries~/.cache/Cypress500 MB–3 GBExpensive

Browser caches are the safest thing on this page — your history, bookmarks, passwords and sessions live in different files that are never targeted. Expect slightly slower first page loads afterwards.

The three Expensive rows are exactly why the staleness gate exists. A Gradle wrapper distribution is a 230 MB download you might need again next month, so by default it survives unless it has been idle for 100+ days.

Developer-tool data​

Not caches — actual installed tooling. These clear the highest bar: a dependency check and the staleness gate.

TargetPathTypical sizeCost
Android emulator images (AVDs)~/.android/avd6–30 GBExpensive
Flutter pub cache~/.pub-cache1–5 GBCheap
Dart analysis server cache~/.dartServer100 MB–1 GBFree
Flatpak user data~/.local/share/flatpak1–10 GBExpensive

Each AVD is treated as an indivisible unit: its .avd directory and sibling .ini are examined together and pruned only when every file in the profile is idle past the threshold. An emulator you booted last month survives.

Flatpak is stricter still — the module refuses to touch the tree at all if any user-scope app is installed, and points you at flatpak uninstall --user --unused instead.

Editor extensions​

Superseded VS Code and Cursor extension versions: the older copies left behind when an extension updates. Removal requires both that a newer version exists and that the old version has been idle past the threshold.

The current version of an extension is never a candidate. See Editor extensions.

Project and personal files — interactive only​

These are never batched and never auto-confirmed. --yes has no effect on them, by design.

TargetWhat it findsCost
Stale node_modulesProject directories untouched for N+ daysCheap (yarn install)
Partial downloads*.fdmdownload, *.crdownload, *.partManual
Stale personal filesFiles in ~/Downloads, ~/Desktop over 10 MB and idle N+ daysManual
The personal-file modes are the only ones that can delete something irreplaceable

node_modules and partial downloads are throwaway by nature. Files in ~/Downloads and ~/Desktop are not — the tool has no way to tell an installer you will never open again from the only copy of a document.

That is precisely why these modes require you to confirm each entry by hand, and why --yes is ignored here. Read each candidate. See Stale personal files.

System cleanup (requires sudo)​

Only runs under --system, and each step asks first.

StepWhat it doesDefault answer
aptapt autoremove --purge -y then apt cleanYes
Journaljournalctl --vacuum-size=100M — hardcoded, not --daysYes
SnapRemoves disabled snap revisionsYes
KernelsLists installed kernels only. Deletes nothing—
/tmpRemoves files with atime older than 7 days — hardcoded, not --daysYes
Page cachesync then vm.drop_caches=3 — frees RAM, not diskNo
--system is Debian/Ubuntu only

The apt steps call apt and dpkg directly with no distro detection and no command -v guard. On Fedora, Arch or openSUSE they fail with "command not found" rather than adapting. Everything else on this page works on any distro. Details: Distro support.

What it refuses to delete​

The allowlist is a hard refusal with no override flag. Any path resolving inside these is rejected, after realpath resolution so a symlink cannot smuggle a path past the check.

CategoryPaths
System roots/, /home, /root, /etc, /boot, /usr, /var, /lib, /sbin, /bin
Home root$HOME itself
Personal data~/Documents, ~/Pictures, ~/Music, ~/Videos, ~/Desktop, ~/Public, ~/Templates
Credentials~/.ssh, ~/.gnupg
Configuration~/.config, ~/.gnome, ~/.mozilla, ~/.thunderbird
Agent state~/.claude, ~/.local/share/claude
Shell initAny file named .bashrc, .zshrc, .profile, .bash_aliases, .bash_history, and similar
Verify this list against your own install

Protected-path lists drift between versions, and some third-party write-ups of this tool list directories that are not actually protected — ~/.password-store and ~/.aws among them.

Do not trust any document, including this one, over your own machine:

npx linux-cleanup --list-targets
npx linux-cleanup --self-test    # asserts the guards actually fire

The complete verified list is at Protected paths.
