为什么会有它​

开发者的电脑会积累大量可再生的垃圾——动辄几十 GB 的软件包管理器缓存、浏览器缓存、构建工具缓存、模拟器镜像，以及两年前就放弃的项目里的 node_modules。

已有的清理工具大多是两种样子之一：要么根本不认识现代开发者缓存，要么是一键清空的工具，把看起来像垃圾的东西都删掉，然后祈祷没出事。

linux-cleanup 的立场正好相反：可脚本化、透明、有白名单保护、默认交互式。 在它碰任何东西之前，您都能确切看到它会碰什么。

设计原则​

出错时选择拒绝。 用白名单，而不是黑名单。工具不认识的路径一律拒绝。用黑名单的话，清理缓存和清空主目录之间只隔着一个拼写错误。

区分缓存和工具。 ~/.cache/yarn 几秒钟就能重新生成；而 Gradle wrapper 发行包是一个 230 MB 的下载，下个月可能还要用。闲置关卡之所以存在，是因为把两者同等对待是错的，1.2.0 改正了这一点。

个人数据由用户来判断。 磁盘上没有任何东西能区分一个再也不会打开的安装包和一份文档的唯一副本。工具拒绝去猜，这就是这些模式忽略 --yes 的原因。

预防胜于恢复。 没有撤销，这是有意的选择——撤销日志会在您正要腾出空间的磁盘上放大写入，还会让人变得粗心。

可审计胜于方便。 用 Bash，因为它本来就装着，而且可以读懂。编译好的二进制文件用起来更顺手，但难以信任得多。

版本检查范围很窄。 启动时，如果在线，命令行会读取一份公开的版本记录。它不会上传清理路径、报告或崩溃包；是否发送报告始终由您决定。

来自纠正的改进​

有两项安全功能，是因为有人指出了真实的问题才有的。

受保护的安装根目录列表来自一个真实的缺陷：pnpm 清理的目标是 ~/.local/share/pnpm——也就是安装根目录——结果删掉了全局安装的包。1.1.0 修复了它，并加了一个断言，保证不会再发生。

闲置关卡来自一位用户的观察：1.2.0 仍会把 Android AVD 整个清掉，而同样的道理应该适用于所有属于工具而非缓存的东西。这就成了 1.2.1。

如果您发现有什么不对，请告诉我们。

参与贡献​

欢迎在 MIT 许可下贡献。

  • 分叉并发起 pull request——不需要特殊权限
  • 报告 bug 或提出功能请求，可以通过 GitHub issues 或邮件
  • main 分支受保护——改动通过经过审查的 PR 合并

编码标准是安全第一、仅离线运行、通过 ShellCheck。见 CONTRIBUTING.md。

只有描述的功能请求和代码一样受欢迎。请说明您希望清理什么，以及现有模式为什么覆盖不到。
